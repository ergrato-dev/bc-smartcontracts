# Teoría 04 — ERC-1155

## 🎯 Objetivos

- Explicar qué es un multi-token y cuándo conviene frente a ERC-20 y ERC-721.
- Usar `balanceOf`, `balanceOfBatch`, `safeTransferFrom` y `safeBatchTransferFrom`.
- Leer los eventos `TransferSingle` y `TransferBatch`, y la URI con `{id}`.
- Reconocer que en ERC-1155 toda transferencia llama al receptor.

---

## 1. Qué problema resuelve

Un juego tiene oro (miles de unidades iguales), espadas legendarias (una de cada) y
escudos (unos pocos iguales). Con lo visto hasta ahora serían un ERC-20 para el oro, un
ERC-721 para las espadas y otro ERC-20 para los escudos: tres contratos, tres
despliegues, tres `approve` para que un mercado los mueva, y una transacción por cada tipo
en un intercambio.

**ERC-1155** ([EIP-1155](https://eips.ethereum.org/EIPS/eip-1155), 2018), el estándar
*multi-token*, guarda muchos tipos de token en un solo contrato. Cada tipo tiene un `id`, y
para cada `id` hay saldos como en ERC-20:

```
balances[id][cuenta] = cantidad
```

Un `id` con un millón de unidades repartidas es fungible, como el oro. Un `id` del que solo
existe 1 unidad se comporta como un NFT. El estándar no los distingue: lo decide el
contrato al emitir.

## 2. Cómo funciona

| Función | Qué hace |
| ------- | -------- |
| `balanceOf(account, id)` | Cuántas unidades del `id` tiene `account` |
| `balanceOfBatch(accounts, ids)` | Varios saldos en una llamada: el de `accounts[i]` en `ids[i]` |
| `safeTransferFrom(from, to, id, amount, data)` | Mueve `amount` unidades de un `id` |
| `safeBatchTransferFrom(from, to, ids, amounts, data)` | Mueve varios `id` a la vez, en una transacción |
| `setApprovalForAll(operator, approved)` | Da permiso a `operator` sobre **todos** tus tokens del contrato |
| `isApprovedForAll(account, operator)` | Si `operator` tiene ese permiso |
| `uri(id)` | La URI de la metadata del `id` |

Tres diferencias con lo anterior:

- **No hay `approve` por cantidad ni por token.** El único permiso es `setApprovalForAll`,
  con el riesgo de la teoría 01: todo o nada.
- **No hay `transferFrom` sin "safe".** Toda transferencia a un contrato llama a
  `onERC1155Received` (o a `onERC1155BatchReceived` en los lotes), que tiene que devolver su
  selector. Lo de la teoría 02 vale aquí en cada envío.
- **No hay `name`, `symbol` ni `totalSupply`** en el estándar. `ERC1155Supply` de
  OpenZeppelin añade el suministro por `id`.

### Los eventos

```solidity
event TransferSingle(address indexed operator, address indexed from, address indexed to, uint256 id, uint256 value);
event TransferBatch(address indexed operator, address indexed from, address indexed to, uint256[] ids, uint256[] values);
```

El `id` va en `data`, no en los topics: no se puede filtrar por `id` con el nodo, solo por
operador, origen y destino.

### La URI con `{id}`

`uri(id)` puede devolver la misma plantilla para todos, con el texto literal `{id}`. Quien
la lee sustituye `{id}` por el `id` en hexadecimal, en minúsculas y con 64 caracteres. El
contrato no hace esa sustitución.

## 3. Cómo se escribe

En `src/Items.sol`, el juego con tres tipos:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.38;

import {ERC1155} from "@openzeppelin/contracts/token/ERC1155/ERC1155.sol";

contract Items is ERC1155 {
    uint256 public constant GOLD = 0;
    uint256 public constant SWORD = 1;
    uint256 public constant SHIELD = 2;

    constructor() ERC1155("https://game.example/items/{id}.json") {
        uint256[] memory ids = new uint256[](3);
        uint256[] memory amounts = new uint256[](3);
        (ids[0], ids[1], ids[2]) = (GOLD, SWORD, SHIELD);
        (amounts[0], amounts[1], amounts[2]) = (1000, 1, 5);
        _mintBatch(msg.sender, ids, amounts, "");
    }
}
```

`_mintBatch(to, ids, amounts, data)` emite varios `id` en una llamada; `_mint(to, id,
amount, data)` emite uno. Los dos son `internal`, y los dos llaman al receptor si `to` es un
contrato. Los arrays de `memory` tienen tamaño fijo (semana 06); la asignación con tuplas
llena tres posiciones en una línea.

### En anvil

Con `anvil --silent &` recién arrancado y las variables de la teoría 01:

```bash
forge create src/Items.sol:Items --private-key "$PK0" --broadcast
I=0x5FbDB2315678afecb367f032d93F642f64180aa3
cast call $I "balanceOfBatch(address[],uint256[])(uint256[])" "[$A0,$A0,$A0]" "[0,1,2]"
cast call $I "uri(uint256)(string)" 1
cast call $I "uri(uint256)(string)" 77
```

```
[1000, 1, 5]
"https://game.example/items/{id}.json"
"https://game.example/items/{id}.json"
```

Los tres saldos en una llamada. `uri` devuelve la plantilla para cualquier `id`, también para
el 77, que no existe: `ERC1155` no lleva la cuenta de qué `id` existen.

Envía 250 de oro a la cuenta 1 y mira el log:

```bash
cast send $I "safeTransferFrom(address,address,uint256,uint256,bytes)" $A0 $A1 0 250 0x --private-key "$PK0" --json | jq -c '.logs[0] | {topics, data}'
```

## 4. Antipatrones y riesgos

**Olvidar que cada envío llama al receptor.** En ERC-721 podías elegir `_mint` para no dar
el control a nadie. En ERC-1155, `_mint`, `_mintBatch` y todas las transferencias llaman a
`onERC1155Received` si el destino es un contrato. Escribe el estado antes de emitir o
enviar, siempre (teoría 02).

**Recibir un lote como si fuera un envío.** Un contrato que implementa
`onERC1155Received` pero no `onERC1155BatchReceived` hace revertir todos los lotes que le
envíen. Si recibes ERC-1155, implementa las dos o hereda `ERC1155Holder` de OpenZeppelin.

**Fiarse de `uri(id)` para saber si un `id` existe.** Devuelve la plantilla para cualquier
número. Si tu contrato tiene que saber qué `id` existen, guárdalo (por ejemplo, con
`ERC1155Supply`, que lleva la cuenta por `id`).

**Asumir que un `id` con 1 unidad es un NFT.** Lo es mientras nadie pueda emitir más. Si
`mint` acepta cualquier cantidad para cualquier `id`, la "espada única" se puede duplicar.
La unicidad es una regla de tu contrato, no del estándar.

**Arrays de distinta longitud.** `safeBatchTransferFrom` y `balanceOfBatch` revierten si
`ids` y `amounts` (o `accounts` e `ids`) no tienen la misma longitud
(`ERC1155InvalidArrayLength`). Un contrato tuyo que reciba arrays emparejados tiene que
comprobarlo igual.

## 5. Trucos

- `cast call $I "supportsInterface(bytes4)(bool)" 0xd9b67a26` comprueba que es un
  ERC-1155.
- Para decodificar un `TransferBatch`, pide los campos no indexados como arrays:
  `cast decode-abi "f()(uint256[],uint256[])" <data>`.
- Si cada `id` tiene su propio archivo, `ERC1155URIStorage` guarda una URI por `id`.

| Necesitas | Estándar |
| --------- | -------- |
| Una moneda, puntos, participaciones | ERC-20 |
| Objetos únicos con dueño, y que cada uno tenga su historia | ERC-721 |
| Muchos tipos en un contrato, con envíos en lote | ERC-1155 |
